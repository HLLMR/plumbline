# Migration guide: Doctrine 0.7 to 0.8

| Field | Value |
|---|---|
| From | Doctrine revision 0.7 |
| To | Doctrine revision 0.8, ratified by `decisions/DR-005.md` |
| Scope | Appendix A (one heading qualifier), Appendix B (B.4/B.7 numbering correction), Part 5 (5.1.3, 5.2.1, new 5.3.8), Part 2 (new 2.28), Part 6 (6.1.3 amended in place), and Part 8 (new 8.7, Protected Control Plane) |
| Applies to | A project bound to 0.7 (DC.4.1) whose Owner wants to move to 0.8 |

## 1. Nothing moves automatically

Moving a project to a later revision is a change-controlled event (Doctrine DC.4.2). This guide is followed only when the project's Owner has explicitly ratified migration in a project-local decision record naming both revisions. No script, adapter, skill, or agent invocation performs this migration on its own initiative, and nothing in this bundle updates an adopting project automatically. Until the Owner ratifies migration, the project remains correctly bound to 0.7.

## 2. What changed

1. **Appendix A.** The charter template's prohibition heading is now provider-contingent: "blocked and logged" becomes "blocked and logged where enforcement exists." A project's own charter carries whichever wording it was instantiated with; migrating updates it only by the Owner's explicit ratification (Doctrine 7.9.1: no agent amends the charter).
2. **Appendix B.** Revision 0.7 had introduced a second heading numbered "B.4" ("Generated boundaries") alongside the pre-existing "B.4" ("BOUNDARIES"), a change-control defect under DC.3.1/DC.3.3. Revision 0.8 corrects this: B.4 keeps its sole original identity, BOUNDARIES, and the generated-boundaries block — with its `<!-- BEGIN/END GENERATED BOUNDARIES -->` markers — moves to a new B.7, appended after B.6. The block's own first line changes from `## B.4 Generated boundaries` to `## B.7 Generated boundaries`.
3. **Part 5.** 5.1.3 now affirmatively requires whatever deterministic dispatch-preparation tooling the revision's own workflow needs (described generically, no product named) and states plainly that a scaffolded skeleton without populated governance records, that tooling, and a ratified adoption record with the adoption commit containing it is not itself adoption. 5.2.1's reference layout gains `governance/templates/`, and new invariant 5.3.8 states that copy is refreshed only by explicit Owner-ratified migration.
4. **Part 2 and Part 6.** New definition 2.28, Birth-test instrument, names the pointer-activated mechanism used only for the active-scope, per-surface birth test (8.3.5.2); 6.1.3 is amended in place to cross-reference it and to name the adoption-recorder lifecycle action as a distinct Owner lifecycle action rather than a birth-test instrument.
5. **Part 8.** New section 8.7, Protected Control Plane: no work order's or birth-test instrument's own capability grant — including one the Owner personally authored — ever authorizes mutation of the active-work-order pointer, the installed enforcement configuration, the active work order/instrument's own frontmatter and body, or the denial-evidence log. Activation, retirement, installed-configuration changes, pointer/active-record changes, a control-plane-mutating recorder action, and the adoption-recorder lifecycle action are Owner lifecycle actions performed outside any capability grant, with authorization recorded before execution in a durable Owner disposition or lifecycle packet (never chat alone); ordinary Part 7 closeout is unaffected. 8.7.4.1-8.7.4.3 define a narrow, machine-readable exception so a birth-test instrument can still name its own canary target: declaring `instrument_kind: birth-test` and listing the exact path in `control_plane_probes` with role `control_plane_falsification_probe` confers no authority and the runtime wall must still deny it; an ordinary work order naming any control-plane path anywhere in its grant fails pre-dispatch validation outright, regardless of labeling.

No other Doctrine clause changed.

## 3. Affected local artifacts

- The project-local work-order template this project's Owner instantiated at adoption: conventionally `governance/templates/B-work-order.md` (Doctrine Appendix B, `ADOPTING.md` section 0). Superseded by a fresh copy of `templates/B-work-order.md` from this distribution's Doctrine 0.8, exactly as originally instantiated. If the project's own pre-dispatch validator implements the `instrument_kind`/`control_plane_probes` rule, its copy must be replaced or updated to the 0.8 behavior for candidate validation to reject protected control-plane mutation targets (see `checks/check_work_order_dispatch.py` in this distribution for the reference behavior).
- The project-local charter template, `governance/templates/A-charter.md`, superseded the same way if the Owner wants the qualified A.1 wording; the live, instantiated charter itself is a separate Owner-ratified record (section 4 step 3).
- Any project-local documentation describing recorder closeout, birth-test instruments, or self-edit protection for the active-work-order file should be reviewed against 8.7 and RFI-22-equivalent local records; 8.7 does not itself change any installed adapter's behavior (D.5.4 of DR-005; that is separate, provider-specific work).

## 4. Preparation procedure

Performed once, by or under the direction of the project's Owner, after migration is ratified:

1. Ratify migration in a project-local decision record naming both revisions (0.7 and 0.8) and listing the affected artifacts (Doctrine DC.4.2).
2. Replace `governance/templates/B-work-order.md` and, if desired, `governance/templates/A-charter.md` with the 0.8 copies from this distribution. Copy them exactly; do not paraphrase (Doctrine 5.1.2, `ADOPTING.md` section 0).
3. Update the project's charter (`A.1`, and `A.2`/`A.3` current-state lines if it names the bound doctrine revision) by Owner ratification (Doctrine 7.9.1: no agent amends the charter).
4. Every project-local grant classification already in force is preserved exactly as issued; this migration changes the template's default shape and adds the B.7 identifier and the `instrument_kind`/`control_plane_probes` schema, and does not retroactively reclassify any surface an Owner has already declared for an issued work order.
5. For every work order prepared from the new template from this point forward, complete the frontmatter first, then run the project's pre-dispatch boundary generator and place its exact output between the `<!-- BEGIN GENERATED BOUNDARIES -->` / `<!-- END GENERATED BOUNDARIES -->` markers under the new `## B.7 Generated boundaries` heading, replacing the placeholder. Do not hand-write the generated block.
6. If the project needs to run an active-scope birth test naming a control-plane path as its canary target, draft the birth-test instrument with `instrument_kind: birth-test` and an exact-path `control_plane_probes` entry per 8.7.4.2, and confirm the project's pre-dispatch validator has been upgraded to this distribution's 0.8 behavior before relying on it; an unupgraded validator will not recognize the new fields.

## 5. Deterministic post-migration check

Before activating a candidate work order prepared under the new template, run the project's pre-dispatch validator in this exact sequence:

```
python checks/check_work_order_dispatch.py --emit-boundaries --work-order <path-to-candidate>
python checks/check_work_order_dispatch.py --work-order <path-to-candidate>
```

The first command must exit 0 and print exactly the block placed under `## B.7 Generated boundaries` (byte-for-byte); any difference means the placed block was not the generator's own output. The second command must exit 0 and print `OK: candidate state is valid`. A nonzero exit from either command is a migration-preparation failure for that work order and blocks activation until corrected.

## 6. What this migration does not do

It does not change any surface a prior, already-issued 0.7 work order declared. It does not touch `DOCTRINE.md`, this repository's own governance instance, or any file outside the artifacts named in section 3. It does not migrate any project other than the one whose Owner ratified it (Doctrine 5.1.5, `DOCTRINE.md` DC.4.1). It does not implement or claim mechanical enforcement of Part 8.7 for any adapter; that is separate, provider-specific work, gated on its own fresh birth test (8.7.4, RFI-22).
