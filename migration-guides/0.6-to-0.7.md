# Migration guide: Doctrine 0.6 to 0.7

| Field | Value |
|---|---|
| From | Doctrine revision 0.6 |
| To | Doctrine revision 0.7, ratified by `decisions/DR-004.md` |
| Scope | Appendix B (work-order template) only. No other Doctrine clause changed (DR-004) |
| Applies to | A project bound to 0.6 (DC.4.1) whose Owner wants to move to 0.7 |

## 1. Nothing moves automatically

Moving a project to a later revision is a change-controlled event (Doctrine DC.4.2). This guide is followed only when the project's Owner has explicitly ratified migration in a project-local decision record naming both revisions. No script, adapter, skill, or agent invocation performs this migration on its own initiative, and nothing in this bundle updates an adopting project automatically. Until the Owner ratifies migration, the project remains correctly bound to 0.6.

## 2. What changed

Doctrine 0.7 aligns Appendix B's default classification with the shipped pre-dispatch validator (`checks/check_work_order_dispatch.py`):

1. The default `enforced_by` value is now the empty inline mapping `enforced_by: {}`, and every one of the eight declared minimum grant surfaces (`filesystem.write`, `filesystem.read.deny`, `shell.execute`, `network.egress`, `package.install`, `secrets.read`, `git.commit`, `git.push`) must be classified exactly once, in `enforced_by` or `unenforced_boundaries`. The 0.6 template classified only `filesystem.write` and left the rest implicit.
2. Appendix B now contains exactly one `<!-- BEGIN GENERATED BOUNDARIES -->` / `<!-- END GENERATED BOUNDARIES -->` marker pair. The block between the markers is replaced with the exact output of the project's pre-dispatch boundary generator (`--emit-boundaries`) after the frontmatter is complete, and the resulting work order is validated before activation.

No other Doctrine clause changed.

## 3. Affected local artifact

The project-local work-order template this project's Owner instantiated at adoption: conventionally `governance/templates/B-work-order.md` (Doctrine Appendix B, the Route B/C scaffolder target under `<your-project>/governance/templates/`, `ADOPTING.md` section 0). It is the only distributed template artifact this migration replaces. It is superseded by a fresh copy of `templates/B-work-order.md` from this distribution's Doctrine 0.7, exactly as originally instantiated (`ADOPTING.md` section 0, `templates/` copied verbatim, never paraphrased). Separately, section 4 step 3 covers a conditional update to the Owner-controlled project charter's revision marker; that is a project record the Owner ratifies, not a distributed artifact this migration replaces.

## 4. Preparation procedure

Performed once, by or under the direction of the project's Owner, after migration is ratified:

1. Ratify migration in a project-local decision record naming both revisions (0.6 and 0.7) and listing this artifact as the one affected (Doctrine DC.4.2).
2. Replace `governance/templates/B-work-order.md` with the 0.7 copy of `templates/B-work-order.md` from this distribution. Copy it exactly; do not paraphrase (Doctrine 5.1.2, `ADOPTING.md` section 0).
3. Update the project's charter (`A.2` / `A.3` current-state lines, if it names the bound doctrine revision) to read `0.7`, by Owner ratification (Doctrine 7.9.1: no agent amends the charter).
4. Every project-local grant classification already in force — the project's own `filesystem.write` allowlist, `filesystem.read.deny` exclusions, and the values chosen for `shell.execute`, `network.egress`, `package.install`, `secrets.read`, `git.commit`, and `git.push` for work orders already issued — is preserved exactly as issued. This migration changes the template's *default* classification shape and adds the generated-boundary markers; it does not retroactively reclassify any surface an Owner has already declared for an issued work order.
5. For every work order prepared from the new template from this point forward, complete the frontmatter first, then run the project's pre-dispatch boundary generator (`--emit-boundaries`) and place its exact output between the `<!-- BEGIN GENERATED BOUNDARIES -->` / `<!-- END GENERATED BOUNDARIES -->` markers, replacing the placeholder. Do not hand-write the generated block.

## 5. Deterministic post-migration check

After step 5 above, before activating the candidate work order, run the same pre-dispatch validator this project already installed at `checks/check_work_order_dispatch.py` in this exact sequence:

```
python checks/check_work_order_dispatch.py --emit-boundaries --work-order <path-to-candidate>
python checks/check_work_order_dispatch.py --work-order <path-to-candidate>
```

The first command must exit 0 and print exactly the block placed between the markers in step 5 (byte-for-byte); any difference means the placed block was not the generator's own output. The second command must exit 0 and print `OK: candidate state is valid`. A nonzero exit from either command is a migration-preparation failure for that work order and blocks activation until corrected; it is never worked around by hand-editing the generated block or by skipping the check.

## 6. What this migration does not do

It does not change any surface a prior, already-issued 0.6 work order declared. It does not touch `DOCTRINE.md`, this repository's own governance instance, or any file outside the one template artifact named in section 3 and, where applicable, the Owner-ratified charter revision marker conditionally updated in section 4 step 3. It does not migrate any project other than the one whose Owner ratified it (Doctrine 5.1.5, `DOCTRINE.md` DC.4.1).
