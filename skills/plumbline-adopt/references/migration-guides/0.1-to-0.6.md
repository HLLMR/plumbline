## PART 0. WHY THIS DOCUMENT EXISTS AND WHAT IT IS NOT

0.1 The 0.1 playbook was written against a charter draft that was never ratified (Doctrine DC.2). An agent began implementing it. Five revisions later the doctrine has changed in ways that make several 0.1 artifacts wrong in place: work-order frontmatter, hook coverage, record layout, brief format, Dispatcher inputs, and the meaning of adoption itself. Left alone, those artifacts would become exactly the kind of stale-but-discoverable truth the doctrine exists to eliminate (5.3.4).

0.2 This document does not adopt the doctrine into the adopting project. Adoption is an Owner event with a defined boundary and a birth test (Part 6 of the doctrine). This document brings both repositories to the state from which the Owner can adopt. Nothing done under it is a work order, nothing it produces claims governed status, and no artifact it touches is represented as having been governed before the adoption commit exists.

0.3 The doctrine's own rules apply to this work even though the doctrine is not yet in force. Concretely: the agent inventories before it changes anything; it moves and marks rather than deletes; it proposes dispositions of intent-bearing content and never decides them; it does not touch project source; it commits nothing without the Owner; and where it does not know, it asks. The Owner may waive any of these for a named item, and the waiver is written into the bootstrap log.

Shell-mediated reads remain unenforced unless the work order's `shell.execute` is `denied`.
