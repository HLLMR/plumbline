Two qualifications travel with every row above and are not footnotes:

2. **The hook cannot make its own availability physical.** A hook that fails to launch or times out does not block the tool call under this provider (D.4.2, last row). "Mechanically enforced" here means *observed denying when the hook runs*, not *impossible to circumvent*.

### D.4.1.0 Enforcement operating envelope

> Plumbline's Claude Code wall is mechanically active only within the specific executing session in which enforcement has been observed. Launch with this repository as the project root; inspect `/hooks` to confirm the matcher, source, and portable command; then, when an Owner-authorized procedure calls for it, run one mutation-capable out-of-grant canary. The wall is live only if the provider blocks the call before mutation, the target remains absent, and the denial log gains exactly one record carrying that executing session's real session ID. `/hooks`, configuration inspection, or direct adapter invocation alone is not proof, and evidence does not transfer between sessions. A session without this evidence must not mutate Plumbline; that prohibition is instruction-only and is not represented as a wall.

This is the charter A.6 text, transcribed. It supersedes the earlier root-and-`/hooks` formulation, which treated a correct `/hooks` display as sufficient. It is not a retraction of that formulation's substance — project root and a loaded Project hook remain necessary — but it records that they are not sufficient, and that proof is per-session rather than per-configuration.

The preflight that establishes this envelope, and the live-wall canary that proves it for a given session, are in `SELF-HOSTING.md` step 6 and `adapters/claude-code/README.md`. An impossible-match `Edit` is not a valid canary: the provider rejects it during input validation, before `PreToolUse` dispatch, so it reaches no hook and writes no denial record.

### D.4.1.1 Observed cause

The hook is registered in this repository's `.claude/settings.json`. The session that ran the probe had its project root in a *different* repository, with this one attached only as an additional working directory. Additional working directories do not contribute hook registrations, and that other repository has no `.claude/` of its own. The hook was therefore never loaded, and a registration that is never loaded blocks nothing.

This is not a defect in the adapter. It is the exact limitation D.4.2's last row names: **the hook cannot make its own availability physical.** The birth test found it on first contact, which is what the birth test is for. A wall assumed rather than observed would have carried this hole into the pilot invisibly.

Retesting requires a Claude Code session whose project root is this repository. That is an Owner action.

**This failed probe is permanent adoption evidence.** It is not superseded or deleted by any later passing run. It demonstrated the boundary of the operating envelope, which is a fact about the provider that remains true after the wall works inside the envelope. A later pass records that enforcement works *within* the envelope; it does not retract that Plumbline is unwalled outside it.

**The later pass is recorded in D.4.0 as event 3, and is itself superseded as proof.** WO-PL-005 changed the adapter's denial logging, so that passing run describes a build that is no longer installed. A birth test is evidence about a specific installation, not a property the adapter keeps across edits. The currently installed build has its own passing Level 1 run, recorded as event 5; event 3 is retained as history and is not the evidence D.4.1 rests on.

### D.4.3 Pilot operating disposition (RFI-13)

Recorded by the Owner (HLLMR), 2026-08-16, in response to the Level 2 finding that a granted shell
is an uncontained mutation channel. It changes none of the observed results in D.4.1 or D.4.2; it
governs how work orders are written given them.

> Adoption proceeds with the declared enforcement gaps. During the first 10 counted work orders, `shell.execute` defaults to `denied`. A work order may use `restricted` only when its objective requires a shell and it explicitly records that filesystem writes, Git, network, packages, secrets, and all other subprocess-reachable boundaries are unenforced-by-declaration. Such a work order makes no claim of repository containment.

The disposition is an operating rule, not an enforcement mechanism. Nothing installed makes
`denied` the default or checks that a `restricted` work order carries the required declaration; both
are honored by the Owner at issuance and by the Reviewer at acceptance. Recorded here so that a
later reader does not mistake a convention for a wall.

### D.7.1 Operational definitions, fixed by the Owner before the first counted work order

Fixed 2026-08-16, satisfying 6.2.1.6 and 9.1.3. Definitions fixed after the fact are not evidence.

**9.2.1 Out-of-grant actions denied.** One denial is one mutation attempt rejected by the enforcement provider and attributable to the active work order. Count raw denial events and identify the surface and mutation channel. Exclude deliberate birth-test and regression-test probes from pilot totals; record those separately. Also record every successful out-of-grant mutation as a deviation. The predicted count is zero.

**9.2.2 RFIs filed.** Count each distinct numbered RFI first opened during the work order. Replies or updates to the same RFI do not create additional counts.

**9.2.3 Drift detection.** One drift instance is one independently remediable mismatch between delivered repository state and the active work order, ratified plan, or routed requirement. "Same-work-order detection" means detection after implementation begins but before the Owner accepts and closes that work order. A mismatch first discovered after closure is later detection and is attributed both to the discovering work order and the earlier accepted work order that introduced it.

**9.2.4 Recovery cost.** One rework cycle begins when the Reviewer or Owner returns an implementation for correction and ends with a new implementation report and review. The initial implementation/review pass is not a rework cycle. Record: rework-cycle count; additional agent sessions required; closed historical artifacts deliberately retrieved to reconstruct intent. The last count is the pilot's archaeology-cost indicator.

**9.2.5 Live corpus and routing gaps.** At activation of each work order, count each distinct document available through Tier-1 injection, deterministic Tier-2 routing, open transactional-record supply, and configured document search or retrieval paths. Count each document once and record both document count and whitespace-delimited word count. Exclude source code and binary assets unless explicitly declared as routed context. Exclude `governance/history/`, `governance/archive/`, root `archive/`, `bootstrap/`, and closed reports unless the active work order explicitly authorizes their retrieval. One routing gap is one declared governed path or subsystem lacking a valid deterministic route at activation. Count orphan Tier-2 documents separately.

**9.2.6 Grant enforcement.** For each work order, enumerate every declared capability surface, including project-specific surfaces. Record: total declared surfaces; mechanically enforced surfaces; unenforced-by-declaration surfaces; and the mechanism and covered mutation channels for each. A partially covered surface is unenforced. A surface counts as mechanically enforced only when every mutation channel capable of reaching it is covered and the installation has passed its birth test.

**9.2.7 Owner reading load.** The unit is whitespace-delimited words assigned as mandatory Owner reading. For an ordinary disposition, count C.1 through C.6 of the Owner brief and exclude reviewer-only notes. The ceiling is **500 words per work order**. When 7.6.3 requires escalation, separately count the brief plus the exact linked evidence the Owner is required to read. The ordinary 500-word ceiling does not apply to escalated evidence, but the triggering 7.6.3 condition must be recorded. Material the Owner opens voluntarily is not mandatory reading load.

**9.2.8 Experimental instruments.** No empirical instrument is qualified at adoption. The pilot conformance gate is Reviewer-only controlled inference. If an experimental instrument is introduced later, one comparison is one independently adjudicable claim evaluated by both the instrument and the Reviewer. Count disagreements and record the Owner's resolution and which assessment was sustained. Otherwise record `N/A`, not zero.

## D.8 Reasoning: why adopt, and why now

Recorded by the Owner (HLLMR), 2026-08-16.

Plumbline is adopting its own Doctrine because a methodology for governing agent work should expose its claims to the same controls it asks others to use. Self-adoption creates a real operating record — work orders, denials, reviews, Owner briefs, drift findings, and recovery costs — without requiring an external adopter to bear the first test of an unpracticed system.

The time to adopt is now because revision 0.6 is ratified, its distribution is reproducible, and the pre-adoption boundary is explicit. Adoption establishes the controlled environment required for the 10-work-order pilot; it does not claim that the method has already succeeded.

## D.9 Rejected alternatives

Recorded by the Owner (HLLMR), 2026-08-16.

1. **Remain pre-adoption while seeking external pilots.** Rejected because Plumbline should bear the first operational cost of its own method.
2. **Treat bootstrap work as retroactively governed.** Rejected because that would falsify the adoption boundary and contaminate the measurements.
3. **Wait for complete enforcement, licensing, publication, or a platform.** Rejected because known enforcement gaps can be declared honestly, and licensing governs publication rather than private adoption.
4. **Rely on instruction without installing and birth-testing the available wall.** Rejected because instruction-only compliance must not be represented as enforcement.
5. **Combine methodology decisions and project-governance decisions into one series.** Rejected because self-hosting depends on preserving the two repository roles.
